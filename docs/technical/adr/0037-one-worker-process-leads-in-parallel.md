# 0037 · One worker process, leads in parallel, sized for about 15 workspaces

- **Status:** accepted, 2026-11-19
- **Context:** the worker was one process with four threads, one workspace per thread, and inside a run one lead at a time through each stage. A run of 50 leads took tens of minutes (each lead makes slow network calls: the site, searches, the model), held one of the four threads all that time, and gave its first draft only near the end, because every lead was researched before any was qualified or written. Ticks for every workspace shared the same four threads every 15 minutes, and work that appeared between ticks waited for the next one. Nothing measured the lag. The target is about **10–15 workspaces** on the current VM, which does not call for several processes.
- **Decision:**
  1. **Leads in parallel.** `Runner` works on a stage's due leads with a bounded thread pool (`WORKER_LEAD_CONCURRENCY`, 4). Each lead's task runs in a copy of the context, so the log and the ledger (`call_scope`) stay per lead. `DeliverStage` opts out (`parallel = False`): it shares mailbox connections.
  2. **Lead by lead.** With `lead_flow`, one task carries a lead through as many stages as it can (research → gate → people → email → copy) before it takes the next, so the first drafts of a run appear within minutes. Each stage still goes through `_process`, so rows, events and per-stage counts are as before. The stage-by-stage order stays for tests and the command line.
  3. **Searches together inside a lead.** Independent searches in research (company news, market news, the careers search; the two people searches; the LinkedIn lookup batches) are made side by side (`stages/together.py`). Results are read in order, so they do not change.
  4. **No waiting for the timer.** A light check every two minutes asks one cheap question per workspace (`CompanyRepository.any_due`) and runs the pipeline only if a lead is due; a pass that moved leads is followed at once by another look. The 15-minute tick keeps the mailbox syncs, the catch-all poll and the rest. A tick more than a whole interval late goes before its workspace's queued run.
  5. **Capacity is settings:** `WORKER_THREADS` (6), `WORKER_LEAD_CONCURRENCY` (4), `WORKER_DATABASE_POOL_SIZE` (8), `DATABASE_POOL_TIMEOUT` (30 s). The worker CLI turns the parallel modes on; `assemble` defaults to one lead at a time.
  6. **Visibility:** every minute the worker logs `worker_status` and writes a heartbeat (its own `platform_settings` row, `id = 'worker'`, so it never changes the settings' version); the admin Overview shows a Worker card (alive, working on, runs waiting and for how long, late passes).
  7. **A separate research model** may be chosen by staff (Vendors → AI models → "Use for research"); nothing changes until they do.
- **Consequences:** a run is several times faster and its first drafts come early; the worker holds up to 6 × 4 leads in flight, which is network-bound and fits the 1 GB limit. With several leads in flight, the credit guard can let each in-flight lead's current step finish past the allowance (the stated policy, "a step that has started finishes"), so the balance may go a little further below nothing than before. The vendors see more calls at once: the shared `HttpClient` honours `Retry-After`, but a vendor with a low limit is watched ([R-55](../tech-debt-and-risks.md)). The database pool is larger, so the **connection budget** (api + worker + one-off commands against the pooler's client limit) must be checked before raising anything ([deployment](../operations/deployment.md)).
- **When to go further (not built):** more than about 30 workspaces, or a second VM, calls for several worker processes. Queued runs are already safe with several workers (`claim_next` uses `SKIP LOCKED`); ticks, light checks and the platform jobs would need leases in the database so two workers do not take the same one. Move to that when the admin card shows runs waiting more than ten minutes, or late passes, at the settings above and a larger VM does not clear it.
- **Alternatives rejected:** several worker processes now (leases, a connection budget for each, more to operate, no gain at this size); a queue such as Celery or Redis (the companies table is the queue, and the project's rule is not to add one); async I/O in the stages (a rewrite of every adapter for what threads already give).
