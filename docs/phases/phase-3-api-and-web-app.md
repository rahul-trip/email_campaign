# Phase 3 — API and web app

**Goal:** give the operator a browser workflow — targets, review, leads, runs and settings — on top of the services the CLI already uses. The UI adds no business logic.

**Depends on:** Phase 2.

**Status (2026-10-17): code complete.** The API has 36 endpoints with 70 tests; a Playwright test walks the whole loop in a real browser against a seeded database with fake vendors; the approval-only gate is tested through the API and the worker. See the [gate record](#gate-record).

**How to run it**

```
uv run outbound auth hash-password        # put the output in OPERATOR_PASSWORD_HASH
# also set SESSION_SECRET in .env
(cd web && npm ci && npm run build)       # once, and after UI changes
uv run outbound serve                     # http://127.0.0.1:8000
uv run outbound worker                    # in a second terminal: executes queued runs
```

**Gate:**
- Nothing reaches the mailbox without an approval made in the web app. The test approves a lead in the review queue, then confirms that a lead nobody approved is never drafted.
- An operator can complete the full loop in the browser: add targets → run → review → draft.

## Scope

**In:**
- FastAPI over the existing services.
- One local login.
- A generated TypeScript client.
- The React app with five screens.
- The signed intake webhook.

**Out:**
- Replies screen (Phase 4).
- Multi-user auth (Phase 6).

## Tasks

### 3.1 API — done

As built: `outbound/api/` (app factory, auth, problem-details errors, schemas, routers), `outbound/worker.py`, and services `leads`, `settings`, `runs`, `dns_check`, `webhook`. Tests: `tests/api/` (auth and errors 12, endpoints 31, gate 3) and `tests/db/test_leads_and_settings.py` (27).

- [x] `outbound/api/app.py`: FastAPI app factory that takes its dependencies from `bootstrap.py`, with request-scoped units of work.
- [x] Routers in `outbound/api/routers/`. Each one is a thin call into a service:

  | Router | Endpoints | Service |
  |---|---|---|
  | `targets` | `POST /targets` (quick add, any anchor), `POST /targets/upload` (preview, then commit), `POST /targets/{row}/confirm`, `PATCH /companies/{id}` (edit saved target) | intake |
  | `review` | `GET /review`, `GET /review/{message_id}`, `POST .../approve` (optional edited body), `POST .../reject` | review |
  | `leads` | `GET /companies` (filters: status, hold reason, campaign), `GET /companies/{id}` (with contacts, emails, messages), `GET /companies/{id}/timeline` (events), `GET /companies/{id}/waterfall` (provider_calls), `POST /companies/{id}/retry`, `POST /companies/{id}/release-hold` | leads, run |
  | `runs` | `POST /runs`, `GET /runs/{id}` (progress, spend), `POST /runs/{id}/cancel` | run |
  | `settings` | sender profile, campaigns, country policies, suppressions, mailboxes, including `POST /mailboxes/{id}/dns-check` | settings |
  | `intake` | `POST /api/intake/webhook` | intake |

- [x] **Runs and the worker.**
  - `POST /runs` inserts a `queued` run.
  - A `outbound worker` process claims queued runs and executes them, polling the `runs` table.
  - The API stays responsive and never runs the pipeline in-request.
  - Cancel sets a flag; the runner checks it between leads.
- [x] **Writes are version-checked.** Every write accepts the `row_version` it read; a stale version returns HTTP 409.
- [x] **Authentication.** One local operator login: an Argon2 password hash comes from the environment and is held in a session cookie. There are no user tables until Phase 6. The app binds to localhost by default.
- [x] **Intake webhook.**
  - Requests carry an HMAC-SHA256 signature over the raw body, using the secret named by `settings.intake_webhook_secret_ref`, plus a timestamp header with a 5-minute window.
  - Each request creates a `webhook` import batch, and intake processes it like any other batch.
  - Requests are idempotent on the sender's event id, which is stored in `import_rows.raw`.
- [x] **Errors.** Problem-details responses (RFC 9457) with stable error codes.

**Done when:** FastAPI test-client tests pass for each endpoint, including the 409 conflict, webhook signature rejection, and replay rejection.

### 3.2 Frontend — done

As built: `web/` with React, TypeScript, Vite, Tailwind, TanStack Query and Router, and a client generated by `openapi-typescript` and `openapi-fetch`. `npm run gen:api` regenerates it from the running code (`scripts/export_openapi.py`); CI fails if the committed copy is out of date. The browser test is `web/e2e/loop.spec.ts`, served by `scripts/e2e_server.py` (real app and worker, fake vendors, throwaway database).

Differences from the text below:
- **Components are small hand-written ones in the shadcn style** (`web/src/components/ui.tsx`), not the shadcn CLI. There are no Radix primitives yet; add them when a dialog or menu is needed.
- **TanStack Router is code-based** (`web/src/router.tsx`), not file-based, which keeps the build to Vite and one plugin.
- **Discovery of the worker:** a run is `queued` by the API and executed by `outbound worker`; the Runs screen polls every two seconds while anything is queued or running.
- The webhook secret is read from the environment variable named by `settings.intake_webhook_secret_ref` (default `INTAKE_WEBHOOK_SECRET`). A repeated event id is answered with `{"duplicate": true}` and changes nothing; a request older than five minutes is rejected.
- Also added beyond the list below: `requalify` (override a disqualification), recording consent for a contact, and `/api/status`, `/api/reports/*` for the dashboards.

- [x] Set up `web/`:
  - React + TypeScript + Vite, TanStack Query and Router, shadcn/ui.
  - `openapi-typescript` generates `web/src/api/schema.ts` from `/openapi.json`. A CI step fails the build if the generated file is out of date.
- [x] Screens:
  - **Review queue (build first).** The email sits beside the research summary, the answers, the lint report and the policy decision. Edit inline, then approve or reject. The result is a diff of the generated text against the edited text.
  - **Targets.** Quick add accepts any anchor. Upload shows a preview with the intake report, then commits. Rows flagged `needs_confirmation` can be confirmed in one click, saved targets can be edited, and targets can be assigned to a campaign.
  - **Leads.**
    - A table filtered by status and hold reason.
    - A detail page with the timeline built from `events`.
    - A waterfall inspector listing each provider tried: outcome, cached or not, and cost.
    - Field history that shows the operator's value next to the engine's value.
    - Retry and release-hold buttons.
  - **Runs.** Start a run (mode, limits), live progress by polling, spend against budget, and cancel.
  - **Settings.** Sender profile, campaigns (titles, fit minimum, research questions, cadence), country policies (with version and reviewer), the suppression list (add only; values are hashed on save), and mailboxes with the DNS check result.
- [x] **Serving.** `uvicorn` serves the built `web/dist` from FastAPI, so there is a single process plus the worker.

**Done when:** a Playwright smoke test walks the full loop against a seeded database with fake providers.

## Closing the phase (what only you can do)

Run it once for real: set the login in `.env`, `outbound serve` and `outbound worker`, add one real target, run, approve one email in the browser, run again, and see the draft in your mailbox Drafts folder. Check that a second, unapproved email stays out of the mailbox.
