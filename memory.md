## Architecture & Conventions
- Specification tracks top-of-funnel email campaigns, including contact discovery, enrichment, verification, drafting via LLMs, staging via mail API (Gmail/Outlook), and automated sequence follow-ups.
- State machine for contacts: `AWAITING_APPROVAL`, `COMPANIES_REACHED`, `FAILED_SENT_RECHECK`, `RESPONSES_RECEIVED`, `AUTOMATED_FOLLOW_UP_ACTIVE`, `SALES_CONVERTED`.

### 2026-07-20 (cont'd) — Contacts swapped to Bright Data LinkedIn Scraper, Proxycurl kept as fallback
- Per user request, added [agent/providers/contacts/brightdata.py](file:///Users/cnc/Downloads/email_capaign/agent/providers/contacts/brightdata.py) (`BrightDataContactProvider`) and made it the **default** contacts provider (`config.example.yaml`'s `providers.contacts: brightdata`, was `proxycurl`). Proxycurl kept registered and selectable via `providers.contacts: proxycurl` — same "swap default, don't delete a working integration" pattern used for the Tavily/Google CSE discovery swap.
- **Architecturally different from every other provider so far:** Bright Data's Dataset API is async (trigger a snapshot job → poll `/progress/{id}` until `status: "ready"` → fetch `/snapshot/{id}`), not a single synchronous request like Proxycurl/Hunter/NeverBounce. `BrightDataContactProvider` implements this as `_trigger_snapshot()` → `_poll_and_fetch()` (bounded by `max_poll_attempts` × `poll_interval_seconds`, defaults 40 × 3s ≈ 120s ceiling) → `_fetch_snapshot()`.
- **Known unknown, documented in the adapter's docstring:** Bright Data offers several distinct LinkedIn datasets (People Search, People Profile, Company...) each with account-specific `dataset_id` and possibly different output field names. The adapter targets the common "LinkedIn People Search" shape (search-by-URL trigger, `name`/`position`/`url`/`about` output fields) with defensive `.get()` fallbacks, same pattern as `proxycurl.py::_build_contact`. **User must confirm output field names match their actual Bright Data dataset** — `_build_contact()` is the one place to adjust if they don't.
- New env vars: `BRIGHTDATA_API_KEY`, `BRIGHTDATA_LINKEDIN_DATASET_ID` (the latter is Bright Data-account-specific — user must create/attach a LinkedIn People Search collector in their Bright Data dashboard and paste its dataset ID).
- `bundle.py` extended with the same "pick the right key based on which provider is configured" pattern already used for discovery (`contacts_api_key` branches on `pnames.contacts`).
- New tests: [test_brightdata_contacts.py](file:///Users/cnc/Downloads/email_capaign/agent/tests/test_brightdata_contacts.py) (8 cases covering the full trigger→poll→fetch flow, poll timeout, failed snapshot status, missing key/dataset_id errors, retry-on-429). **56/56 tests passing** (was 48).
